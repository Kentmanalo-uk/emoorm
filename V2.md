# E-MOORM AI Handoff

## 1. Project Overview

**Project:** E-MOORM, a hyperlocal marketplace for local entrepreneurs, farmers, cooperatives, MSMEs, and consumers in Oriental Mindoro, Philippines.

**Main features:** Public product/store browsing, search and image search, buyer accounts, carts and checkout, delivery/pickup orders, payment proof/GCash references, reviews, wishlists, followed stores, buyer-store messaging, notifications, seller applications and seller operations, returns/refunds, and web-based municipal/super-admin moderation.

**Architecture / stack:**
- `backend/`: Node.js Express REST API, CommonJS JavaScript, Prisma 5, MySQL/MariaDB.
- `web/`: React 19 + Vite, React Router, Axios, TanStack Query, Zustand, React Hook Form, Tailwind/PostCSS, Phosphor icons.
- `mobile/`: React Native 0.86 + Expo SDK 57 + Expo Router, Axios, Zustand, AsyncStorage, Phosphor icons.
- Both clients consume the REST API; neither accesses the database directly.

**Important folders:** `backend/src/` (API layers), `backend/prisma/` (schema/migrations/seed), `web/src/` (pages/components/state/styles), `mobile/app/` (Expo routes), `mobile/src/` (API/theme/state/components), and `backend/uploads/` / `backend/uploads-private/kyc/` (public media and protected KYC files).

## 4. Backend / Database

**Backend architecture:** Route registration -> middleware/validation -> controllers -> services/repositories -> Prisma/MySQL. Main route aggregator: `backend/src/routes/index.js`. Standard API response shape is generally `{ success, message, data }`.

**Database:** MySQL/MariaDB through Prisma. Current models include users, municipalities, stores, service areas, products, inventory movements, carts, wishlists, orders/items/status history, reviews, reports, notifications/push tokens, conversations/messages, returns, support tickets, banners, vouchers, app settings, audit logs, QR sessions, and related redemption records. Important relationships include:
- Users belong to a municipality and may own one store.
- Stores belong to a municipality and have products, service areas, orders, followers, and messages.
- Products belong to stores/categories and have approval status and inventory history.
- Orders contain item price snapshots and status history, with buyer/store/payment/fulfillment data.
- Reviews relate buyers to purchased products and can include media and seller replies.

**API areas:** `/api/auth`, `/municipalities`, `/categories`, `/stores`, `/products`, `/orders`, `/reviews`, `/reports`, `/notifications`, `/upload`, `/analytics`, `/audit-logs`, `/announcements`, `/admin`, `/auth/mfa`, `/auth/qr`, `/messages`, `/follows`, `/addresses`, `/returns`, `/support`, `/banners`, `/vouchers`, and `/app-settings`.

**Authentication/security:** JWT access and refresh tokens, bcrypt password hashing, Google OAuth, password reset, admin MFA/TOTP, QR login, account active/deleted checks, rate limiting, CORS/origin checks, Helmet, compression, and protected KYC file access. Authorization middleware checks role, active user, municipality assignment/scope, and store ownership. Municipality enforcement across every route has not been independently audited: **UNKNOWN**.

**Environment variable names (no values):** `NODE_ENV`, `PORT`, `API_PREFIX`, `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `JWT_REFRESH_SECRET`, `JWT_REFRESH_EXPIRES_IN`, `BCRYPT_ROUNDS`, `CORS_ORIGIN`, `ALLOWED_ORIGINS`, `MAX_FILE_SIZE`, `UPLOAD_DIR`, `PRIVATE_UPLOAD_DIR`, `ALLOWED_FILE_TYPES`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `FRONTEND_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `DEFAULT_PAGE_SIZE`, `MAX_PAGE_SIZE`, `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX_REQUESTS`, and `BODY_LIMIT`.

## 5. User Roles & Permissions

- **Buyer:** Default registered role. Can browse/search, manage profile and addresses, use wishlist/cart/checkout, place and track orders, review qualifying purchases, report content, message stores, and apply to become a seller.
- **Seller:** Buyer capabilities plus one store, product/inventory management, store settings, seller messaging, order fulfillment, returns handling, analytics/finance, reviews, and payment/fulfillment settings. Seller routes are guarded by `SELLER` (with selected super-admin access).
- **Municipal Admin / Junior Admin:** Assigned to one municipality. Can moderate local seller applications, products, reports, sellers, and municipal data/analytics. Middleware restricts access to the assigned municipality; exact enforcement on every route is **UNKNOWN**.
- **Superadmin:** Platform-wide administration, including users/roles, municipalities, categories, banners, vouchers, announcements, audit logs, app settings, reports, and broader analytics.

Buyer and seller are persisted roles, not merely a visual toggle. The verified implementation supports seller application followed by administrative role approval/update and role-aware navigation; a separate buyer/seller mode-switch contract is **UNKNOWN**. Never assume a user can access seller actions without the server-side role check.

## 6. Important Existing Workflows

- **Registration/login:** User registers as buyer, logs in with JWT access/refresh tokens, can reset password; Google OAuth, MFA, and QR login paths also exist.
- **Seller application:** Buyer submits seller/business information and application materials; admin approval changes access to seller capabilities. Seller KYC files are protected.
- **Buyer/seller access:** Clients redirect to buyer or seller areas based on the authenticated role. Seller operations are separate from buyer browsing; the exact UI for switching modes is **UNKNOWN**.
- **Product browsing:** Guests and buyers browse products, categories, stores, text search, and image-search results. Product approval/moderation is part of the backend flow.
- **Product creation:** Seller creates/updates products, including multi-image upload and inventory-related data; administrative approval is required where enforced by status.
- **Cart/checkout:** Persistent cart, per-store grouping, quantity/stock handling, totals, addresses, delivery/pickup availability, coverage checks, and store-compatible payment methods.
- **Payment proof / GCash:** Checkout supports payment-proof upload and store QR/payment settings. Payment is handled through the current application workflow; external provider settlement is **UNKNOWN**.
- **Orders:** Checkout creates orders per store. Buyers view/group orders, cancel where allowed, buy again, view receipts, and contact sellers. Sellers manage fulfillment-aware status transitions.
- **Delivery/pickup:** Store fulfillment settings and checkout availability determine delivery/pickup options; detailed logistics integration is **UNKNOWN**.
- **Reviews:** Qualifying order items can receive ratings/comments and media; sellers can reply. Mobile uses multipart upload and must send backend-expected `userId`.
- **Messaging/notifications:** Buyer-store conversations, conversation threads, unread counts/badges, notifications, and polling are implemented. Push registration is not complete.
- **Admin/municipality:** Web-only admin screens cover users, sellers, products/categories, municipalities, reports, banners, vouchers, announcements, audit logs, settings, and municipal moderation.
- **Returns/refunds:** Return requests and seller/admin handling are represented in API, schema, and seller UI. Live end-to-end behavior is **UNKNOWN**.
